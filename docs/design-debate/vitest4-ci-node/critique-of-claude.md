## Important

1. **`setup-node 18` では、約束している最低版 18.11 を検査できない。**

   `node-version: 18` が選ぶのは 18 系の新しい版であり、`v18.` の確認でもこの穴は埋まらない。18.11 より後に追加された API を使っても CI が通り、18.11 の利用者だけが壊れる可能性がある。型検査についても、設計自身がグローバル API の検出漏れを認めている。

   最低版への約束を検査する job なら、実行環境は `18.11.0` に固定するべき。最新の 18 系を使うなら、「18.11 の検証ではない」という制限を明記する必要がある。

2. **「rc 0 ＋ connector 名が全部出る」は、互換性の故障を成功と判定する。**

   [pipeline.ts](/Users/wharfe/dev/cronscope/src/pipeline.ts:15) は、connector 内の例外を捕捉し、`unavailable` に変換する。例えば availability 内で Node 18 に存在しない API を呼ぶと、名前付きの unavailable 行が出て、scan は rc 0 になり得る。提案された条件をそのまま満たす。

   保存された snapshot の `thrownBy` が存在しないことを検査し、想定した unavailable と例外による unavailable を区別する必要がある。さらに、空の HOME では成功経路の大半が動かない。「起動確認」として採用するのは妥当だが、表の「新しいグローバルは scan の経路で呼ばれたとき検出」は現状の判定条件では成立しない。

3. **全 `.js` の import は、副作用のない読み込み検査になっていない。**

   [cli.ts](/Users/wharfe/dev/cronscope/src/cli.ts:1) は末尾で無条件に `main()` を実行する。import すると、引数のない場合は scan が走り、snapshot を書く。設計では空の HOME を明記しているのは後続の scan だけなので、import 段階で runner の通常 HOME に書き込む可能性がある。import の完了も、そこで開始された `main()` の完了を意味しない。

   CLI は隔離した環境で子プロセスとして実行し、その他のモジュールだけを import する形にするべき。構文検査が目的の部分は `node --check` で済ませられる。全 import を残すなら、その subprocess 全体にも HOME・環境変数の隔離を適用する必要がある。

## Minor

1. **型検査のために、CI 内で別の依存解決を追加する費用が過小評価されている。**

   `npm install --no-save @types/node@18.11` は追加通信と依存ツリーの変更を伴う。`--no-save` は「検査用の隔離環境」を意味しない。型だけでも、検査対象の解決結果と CI の再現性には影響する。

   この段を採るなら、採用版と実際に解決された型の確認方法まで定めるべき。CI 変更最小という制約を優先するなら、まず最低版の起動検査だけに絞り、型検査の追加価値を別途判断する方が単純。

2. **検出力の比較表が、現在と提案の双方を強く言いすぎている。**

   現在も「18 での挙動差」を検出できるのはテストが通る経路だけ。提案側も全 module の import では、関数内の遅延 import や未実行の API 呼び出しまで検査できない。表は保証ではなく「実行・型検査した範囲で検出」と書き分けるべき。
